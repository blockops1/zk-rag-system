# PRD — Phase S: Provenance UI

## Context

Phase S adds a rich, interactive ZK proof UI to the website search results. The core insight is that ZK proof generation (via the Rust `prove-bin` binary) is fast (<1s locally), while on-chain zkVerify verification via Kurier takes longer. This asymmetry drives the UX split: generate proof immediately on search, verify on-demand.

## Glossary

| Term | Meaning |
|------|---------|
| **ZK Proof** | Plonky2 SNARK proof generated by `prove-bin` from Merkle path data |
| **public_inputs** | The 3 public values every proof contains: `leaf_hash`, `document_hash`, `merkle_root` |
| **leaf_hash** | `Poseidon(chunk_text)` — cryptographic hash of the chunk content |
| **document_hash** | `Poseidon(doc_id_bytes)` — the Merkle tree's leaf[0], pre-committed on-chain |
| **merkle_root** | Root of the document's Merkle tree, also committed on-chain |
| **Kurier / zkVerify** | Third-party service that attests proofs on-chain; verification is the slow step |
| **Provenance** | Proof that a specific passage comes from a specific document at a specific time |

## UX Flow

```
User types query → hits Search
    │
    ├─ Backend: query Qdrant
    ├─ Backend: for each result chunk, fire generateProof() in parallel (background)
    └─ Frontend: results appear with ZK Proof buttons (spinner while generating)

Each passage card:
    ┌──────────────────────────────────────────────────────┐
    │ Page 47                              Score: 0.87     │
    │ "When conducting urban operations, commanders..."      │
    │                                                      │
    │ [Read full section]      [ZK Proof ▾]                │
    └──────────────────────────────────────────────────────┘

User clicks "ZK Proof ▾" → expands:

    [ZK Proof ▾]
      ├─ [Download ZK Proof]
      ├─ [Verify]
      ├─ [Doc Hash]
      ├─ [Explain]
      └─ [Decode]

User clicks [Verify]:
      ├─ Backend: POST /api/provenance/submit → returns job_id
      ├─ Frontend: shows greyed [Verification ▾]
      │
      └─ Polling loop:
            GET /api/provenance/status/{job_id}
            └─ Once "finalized"/"verified": [Verification ▾] becomes active
                   └─ Click → shows verification result (success/fail + explorer link)
```

## API Changes

### New: `POST /api/provenance/generate`

Generates a ZK proof for a chunk locally via `prove-bin`.

**Request:**
```json
{"chunk_id": "00c8a75d...-42"}
```

**Response (200):**
```json
{
  "chunk_id": "00c8a75d...-42",
  "proof_hex": "0x1a2b3c...",
  "public_inputs_hex": "0x...",
  "vk_hex": "0x...",
  "public_inputs": {
    "leaf_hash": "0x...",
    "document_hash": "0x...",
    "merkle_root": "0x..."
  },
  "doc_id": "00c8a75d...",
  "leaf_index": 43,
  "tree_depth": 7,
  "merkle_root": "0x..."
}
```

**Error (400):** Invalid chunk_id format  
**Error (404):** chunk_id not found in any collection  
**Error (500):** prove-bin failure

**Caching:** Result cached in `_provenance_jobs[chunk_id]` under key `"proof"`. Subsequent calls return cached result instantly.

---

### New: `POST /api/provenance/submit`

Submits a pre-generated proof to Kurier/zkVerify.

**Request:**
```json
{"chunk_id": "00c8a75d...-42"}
```

**Response (200):**
```json
{
  "chunk_id": "00c8a75d...-42",
  "job_id": "abc123",
  "status": "submitted"
}
```

**Error (400):** Missing required fields  
**Error (404):** Proof not yet generated (call `/generate` first)  
**Error (500):** Kurier API error

---

### Changed: `GET /api/provenance/{chunk_id}`

Existing endpoint. Now also sets/returns `zk_proof.public_inputs` and `zk_proof.proof_hex` from cache when available.

---

### Changed: `GET /api/provenance/{chunk_id}/status`

Unchanged. Returns Kurier job status: `pending | submitted | processing | finalized | failed`.

## Frontend Changes

### ZK Proof Button States

| State | Appearance | Trigger |
|-------|-----------|---------|
| Generating | `[⚙ Proving...]` — disabled, spinner | Proof not yet generated |
| Ready | `[ZK Proof ▾]` | Proof generated, ready to expand |
| Verifying | `[Verify]` becomes `[Verification ▾]` (greyed) | Submit sent to Kurier |
| Verified | `[Verification ▾]` active | zkVerify job finalized |

---

### Sub-Buttons

#### Download ZK Proof
- **Action:** `GET /api/provenance/generate/{chunk_id}` → response → download as `.json`
- **File name:** `zk-proof-{chunk_id}.json`
- **Contents:**
```json
{
  "chunk_id": "...",
  "doc_id": "...",
  "leaf_index": 43,
  "tree_depth": 7,
  "merkle_root": "0x...",
  "public_inputs": {
    "leaf_hash": "0x...",
    "document_hash": "0x...",
    "merkle_root": "0x..."
  },
  "proof_hex": "0x...",
  "vk_hex": "0x...",
  "vk_id": "..."
}
```

#### Verify
- **Action:** `POST /api/provenance/submit` with `{chunk_id}`
- **Result:** `{job_id}` → starts polling `GET /api/provenance/status/{job_id}`
- **UI:** On submit, greyed `[Verification ▾]` appears below Verify
- **Poll:** every 2s, up to 60 attempts (2min timeout)
- **Completion:** `[Verification ▾]` becomes clickable; click shows:
  - Success: green checkmark + "Verified on zkVerify" + link to explorer
  - Failed: red X + "Verification failed" + error detail

#### Doc Hash
- **Action:** Opens new tab to `https://sepolia.explorer.horizen.io/block/{evm_block_number}`
- **Data source:** `evm_block_number` from passage metadata

#### Explain
- **Action:** Opens new tab to `https://github.com/youruser1/zk-prover-verifier-plonky2`
- **Label:** `[Explain]`

#### Decode
- **Action:** Opens modal showing human-readable breakdown of `public_inputs`
- **Modal content:**
  ```
  This ZK proof demonstrates that the retrieved passage is part of an authentic
  military document that was processed and committed to the Horizen blockchain.

  ┌─────────────────────────────────────────────────────────────┐
  │ PUBLIC INPUTS                                               │
  ├──────────────────┬──────────────────────────────────────────┤
  │ leaf_hash       │ Poseidon(chunk_text)                     │
  │ 0x1a2b3c...     │ Hash of this specific passage text     │
  ├──────────────────┼──────────────────────────────────────────┤
  │ document_hash   │ Poseidon(doc_id)                        │
  │ 0xdef456...     │ Identifies the source document          │
  ├──────────────────┼──────────────────────────────────────────┤
  │ merkle_root     │ Root of the document's Merkle tree       │
  │ 0x789abc...     │ Pre-committed on Horizen at block #1234 │
  └──────────────────┴──────────────────────────────────────────┘

  Circuit logic:
  1. Given the chunk text, the circuit recomputes Poseidon(chunk_text) → leaf_hash
  2. Using the Merkle path (siblings + leaf_index), it recomputes merkle_root
  3. The circuit verifies: recomputed_leaf_hash == public_input.leaf_hash
                          AND recomputed_root   == public_input.merkle_root
                          AND merkle_root       == document_hash (via Poseidon commitment)
  4. The EVM ingestion timestamp and block are embedded as private inputs

  What this means:
  • The passage text has NOT been modified since the document was processed
  • The passage is cryptographically linked to the document hash committed on-chain
  • The on-chain record proves WHEN the document was first processed
  ```
- **Decode link:** Uses `leaf_hash` from public_inputs — user can compare this to what they get by hashing the passage text themselves

## Pre-generation Strategy

On search, fire `POST /api/provenance/generate` for each passage chunk in parallel (Promise.all). Use `Promise.allSettled` so one failure doesn't block others. Backend will cache results.

For a 5-result search: all 5 proofs generate in <1s total (parallel).
